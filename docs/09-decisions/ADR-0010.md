## Kontext

tarifnova und blocpress haben je acht Methodik- und Code-Skills, alle leicht
verschieden. Die Namen sind gemischt (deutsch/englisch, mal Artefakt, mal Tätigkeit).
`arc42` macht eigentlich eine Architektur-Impact-Analyse. Kurze allgemeine Namen wie
`adr` können mit anderen Skill-Paketen kollidieren, zumal die Skills als Kopie in
`.agents/skills/` ohne Plugin-Präfix liegen (ADR-0009).

Für neue Projekte fehlt ein Einstieg, der zur Vision führt. Für die Migration
bestehender Projekte fehlt ein Skill, der vorhandenen Code und vorhandene Doku
übernimmt.

## Entscheidung

### Namen

Englisch, gemeinsamer Präfix `spine-`, ein Verb je Schritt im Lebenszyklus. Die
Gesprächsführung erfolgt in der Projektsprache (ADR-0011).

| Skill | Aufgabe | bisher |
|---|---|---|
| `spine-init` | neues Projekt starten, führt zur Vision | — |
| `spine-adopt` | bestehendes Projekt mit Code und Doku übernehmen | — |
| `spine-require` | Anforderung formulieren (Epic, Story, Requirement) | `anforderung` |
| `spine-impact` | Wirkung auf die Architektur prüfen und Kapitel pflegen | `arc42` |
| `spine-decide` | Entscheidung als ADR festhalten | `adr` |
| `spine-build` | umsetzen, Test, Status nachziehen | `umsetzung` |
| `spine-prove` | Nachweis Anforderung ↔ Test prüfen | `nachweis` |
| `spine-gate` | Gate in den Build des Projekts einhängen | — |

Nicht Teil von docspine: die Code-Qualitäts-Skills (`compiler-guard`, `srp-splitter`,
`test-tracker`), `agent-orchestrator` (Claude-spezifisch) und die projekteigenen
Skills von tarifnova.

### spine-init

1. **Zustand erkennen.** Gibt es schon Code oder Doku, weiter zu `spine-adopt`.
2. **Gespräch zur Vision, vorschlagend statt fragend.** Aus der ersten Beschreibung
   formuliert der Skill Entwürfe zu Problem, Zielgruppe, Kernsatz, Erfolg,
   Nicht-Zielen und Randbedingungen. Der Mensch bestätigt, korrigiert oder sagt
   „weiß ich noch nicht“. Kein hartnäckiges Nachfragen.
3. **Pflicht ist nur der Kernsatz der Vision.** Alles andere darf offen bleiben.
4. **Ein `UNKNOWN` trägt seine offene Frage mit** („UNKNOWN — offene Frage: …“).
   `STATUS.md` listet alle offenen Fragen. Spätere Skills greifen sie auf, wenn ein
   Thema sie berührt.
5. **Vorschlag im Chat, dann Freigabe, dann schreiben:**

   | Antwort | Ziel |
   |---|---|
   | Problem, Zielgruppe, Kernsatz, Erfolg, Nicht-Ziele | `01-goals/vision.md` |
   | Top-Qualitätsziele | `vision.md`, zusätzlich REQ mit `category: quality`, `status: proposed` |
   | 3–7 Themen | `01-goals/epics/`, `status: open` |
   | Randbedingungen | `02-constraints.md` |
   | schon getroffene Entscheidungen | `09-decisions/`, `status: proposed` |
   | Sprache, Normen, Module | `PROFILE.md` |

6. **Gerüst:** README, `STANDARD.md`, `AGENTS.md`, `.agents/skills/`, Link unter
   `.claude/`. Leere Kapitel entstehen nicht.
7. **Prüfen** mit der Generator-CLI (ADR-0012), ohne Build-Anbindung.

Die Build-Anbindung ist bewusst ein eigener Schritt (`spine-gate`), weil sie vom
Stack abhängt und viele Einzelheiten hat. `spine-gate` erklärt jeden Schritt und
schreibt erst nach Freigabe.

## Konsequenzen

- Beim Tippen von `/spine-` zeigt die Vervollständigung die ganze Familie.
- `spine-adopt` ist der Weg für die Migration von tarifnova, blocpress und 3dPacMan.
- 3dPacMan (`VISION.md` und fünf Epics) dient als Vergleichsfall für `spine-init`.
