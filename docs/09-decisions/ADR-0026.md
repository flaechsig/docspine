## Kontext

Das Ursprungsprojekt und blocpress haben je acht Methodik- und Code-Skills, alle leicht
verschieden. Die Namen sind gemischt (deutsch/englisch, mal Artefakt, mal Tätigkeit).
`arc42` macht eigentlich eine Architektur-Impact-Analyse. Kurze allgemeine Namen wie
`adr` können mit anderen Skill-Paketen kollidieren, zumal die Skills als Kopie in
`.agents/skills/` ohne Plugin-Präfix liegen (ADR-0009).

Bis 0.19 trugen die Skills den Präfix `spine-` (ADR-0010). Inzwischen gibt es weitere
Werkzeuge nach demselben Muster, etwa secspine mit Skills `secspine-*`. Liegen mehrere in
einem Projekt, ist `spine-` mehrdeutig: Es sagt nicht, zu welchem Werkzeug ein Skill
gehört, und ein Update von docspine überschreibt alle Ordner mit diesem Präfix.

Für neue Projekte fehlt ein Einstieg, der zur Vision führt. Für die Migration
bestehender Projekte fehlt ein Skill, der vorhandenen Code und vorhandene Doku
übernimmt.

## Entscheidung

### Namen

Englisch, gemeinsamer Präfix `docspine-` (der Produktname, wie `secspine-` bei secspine), ein Verb je Schritt im Lebenszyklus. Die
Gesprächsführung erfolgt in der Projektsprache (ADR-0011).

| Skill | Aufgabe | bisher |
|---|---|---|
| `docspine-init` | neues Projekt starten, führt zur Vision | — |
| `docspine-adopt` | bestehendes Projekt mit Code und Doku übernehmen | — |
| `docspine-require` | Anforderung formulieren (Epic, Story, Requirement) | `anforderung` |
| `docspine-impact` | Wirkung auf die Architektur prüfen und Kapitel pflegen | `arc42` |
| `docspine-decide` | Entscheidung als ADR festhalten | `adr` |
| `docspine-build` | umsetzen, Test, Status nachziehen | `umsetzung` |
| `docspine-prove` | Nachweis Anforderung ↔ Test prüfen | `nachweis` |
| `docspine-gate` | Gate in den Build des Projekts einhängen | — |
| `docspine-update` | ein Update von docspine im Projekt abschließen (ADR-0016) | — |

Nicht Teil von docspine: die Code-Qualitäts-Skills (`compiler-guard`, `srp-splitter`,
`test-tracker`), `agent-orchestrator` (Claude-spezifisch) und die projekteigenen
Skills des Ursprungsprojekts.

### docspine-init

1. **Git prüfen.** Ohne Git bricht der Skill ab. Ist der Ordner noch kein Repository,
   schlägt er `git init` vor (ADR-0021).
2. **Sprache klären.** Als Erstes auf Englisch nach der Projektsprache fragen, mit
   einem aus der ersten Nachricht geratenen Vorschlag. Danach läuft das Gespräch in
   dieser Sprache (ADR-0014).
3. **Zustand erkennen.** Gibt es schon Code oder Doku, weiter zu `docspine-adopt`.
4. **Gespräch zur Vision, vorschlagend statt fragend.** Aus der ersten Beschreibung
   formuliert der Skill Entwürfe zu Problem, Zielgruppe, Kernsatz, Erfolg,
   Nicht-Zielen und Randbedingungen. Der Mensch bestätigt, korrigiert oder sagt
   „weiß ich noch nicht“. Kein hartnäckiges Nachfragen.
5. **Pflicht ist nur der Kernsatz der Vision.** Alles andere darf offen bleiben.
6. **Ein `UNKNOWN` trägt seine offene Frage mit** („UNKNOWN — offene Frage: …“).
   `01-goals/README.md` listet alle offenen Fragen. Spätere Skills greifen sie auf, wenn ein
   Thema sie berührt.
7. **Vorschlag im Chat, dann Freigabe, dann schreiben:**

   | Antwort | Ziel |
   |---|---|
   | Problem, Zielgruppe, Kernsatz, Erfolg, Nicht-Ziele | `01-goals/vision.md` |
   | Top-Qualitätsziele | `vision.md`, zusätzlich REQ mit `category: quality`, `status: proposed` |
   | 3–7 Themen | `01-goals/epics/` (Status wird abgeleitet) |
   | Randbedingungen | `02-constraints.md` |
   | schon getroffene Entscheidungen | `09-decisions/`, `status: proposed` |
   | Sprache, Normen | `PROFILE.md` |

8. **Gerüst:** `STANDARD.md` (englisch, unverändert kopiert), `README.md` (aus
   `standard/en/README.md` in die Projektsprache übersetzt, mit Versionskopf, ADR-0014),
   `AGENTS.md`, `.agents/skills/`, Link unter `.claude/`. Leere Kapitel entstehen nicht.
9. **Prüfen** mit der Generator-CLI (ADR-0012), ohne Build-Anbindung.
10. **Erster Commit** auf dem Hauptzweig, danach das Angebot, ein vom Team schon
   angelegtes Remote zu verbinden (ADR-0021).

Die Build-Anbindung ist bewusst ein eigener Schritt (`docspine-gate`), weil sie vom
Stack abhängt und viele Einzelheiten hat. `docspine-gate` erklärt jeden Schritt und
schreibt erst nach Freigabe.

## Konsequenzen

- Jedes Werkzeug der Familie reserviert seinen eigenen Präfix; die Skills mehrerer
  Werkzeuge liegen ohne Kollision nebeneinander unter `.agents/skills/`.
- Projekte, die von 0.19 oder älter kommen, haben noch Ordner `.agents/skills/spine-*`.
  Die Installation löscht nichts; `docspine-update` schlägt vor, sie zu entfernen
  (Standard 2.2).
- Die Namen sind länger, `/docspine-` statt `/spine-`.
- Beim Tippen von `/docspine-` zeigt die Vervollständigung die ganze Familie.
- `docspine-adopt` ist der Weg für die Migration des Ursprungsprojekts, von blocpress und 3dPacMan.
- 3dPacMan (`VISION.md` und fünf Epics) dient als Vergleichsfall für `docspine-init`.
