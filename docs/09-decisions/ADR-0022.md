id: ADR-0022
title: Prüfung nach dem Build als eigener Schritt, Testberichte selbst finden
status: proposed
date: 2026-10-05

---

## Kontext

ADR-0019 legt fest, dass die Prüfung nach den Tests läuft und den Build bei Fehlern
scheitern lässt. Bei der Migration von blocpress (fünf Maven-Module) musste dafür ein
eigenes Modul ohne Code als letztes Modul im Reactor stehen, weil Maven 3 keinen Schritt
„nach allen Modulen“ kennt. Außerdem musste jeder Berichtsort einzeln im Profil stehen.
Beides ist umständlich; ein neues Modul wäre still ohne Nachweis geblieben.

Die Prüfung läuft ohnehin nach dem Build, wenn die Skills sie aufrufen. Damit sie nicht an
der KI hängt (ADR-0009), braucht es aber einen Ort, an dem sie ohne KI läuft.

## Entscheidung

- **Die Prüfung findet die Testberichte selbst:** jede XML-Datei im Repository, deren
  Wurzel eine Testsuite ist. `test_reports` im Profil wird optional und schränkt die
  Suche nur noch ein.
- **Die Prüfung darf als eigener Schritt direkt nach dem Build laufen,** statt im Build.
  Dann führt die CI diesen Schritt aus, damit nichts ungeprüft auf den Hauptzweig kommt.
  Lokal rufen Skills und `AGENTS.md` ihn nach dem Build auf.
- Für Maven mit einem Modul bleibt der Aufruf in `verify` die einfachste Lösung; für
  mehrere Module beschreibt die Integration den eigenen Schritt.

Verworfen:
- **Ein Zusatzmodul als letztes im Reactor:** funktioniert, ist aber ein Modul ohne Code
  nur für den Aufruf.
- **Jedes Modul prüft seine eigenen Ergebnisse:** deckt einen Teil der Fehler ab, aber
  ob ein Requirement überhaupt belegt ist, entscheidet sich erst nach allen Modulen.

## Konsequenzen

- Keine Änderung an POMs für Projekte mit mehreren Modulen; eine Zeile in der CI.
- Ein lokales `mvn verify` allein prüft die Doku bei solchen Projekten nicht mehr.
- Veraltete Berichte aus einem früheren Build zählen mit, bis der nächste Build sie
  ersetzt; das gilt auch für fest eingetragene Orte.
