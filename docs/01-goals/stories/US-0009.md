Als **Projektverantwortlicher** möchte ich ein bestehendes Projekt mit Code und Doku in den Standard überführen lassen, damit die Migration geführt und nicht von Hand geschieht.

**Hintergrund.** Weg für die Migration der drei Projekte (ADR-0010).

**Erfahrungen aus der Migration von blocpress (2026-10-05),** als Grundlage für den Skill:
1. Projektfremdes aus `docs/` herauslösen (dort: die Website, die GitHub Pages aus `docs/`
   veröffentlichte, nach `site/` mit eigenem Workflow), Pfade in Tests und Workflows
   nachziehen.
2. Installieren; vorhandene `.claude/skills/` vorher auflösen: Methodik-Skills entfallen,
   projekteigene nach `.agents/skills/`.
3. Inhalte umziehen (`git mv`, damit die History bleibt): Spec nach `01-goals/`, ADRs von
   AsciiDoc in Markdown mit vierstelligen Nummern, arc42-Kapitel mit Inhalt in
   Kapiteldateien, Altbestand und alte ROADMAP nach `docs/legacy/`, generierte Ansichten
   und `CONVENTIONS.md` löschen.
4. Schema angleichen: Epic-IDs in Großbuchstaben, `obligation` englisch, Epic-Status und
   `confidence` raus, `evidence` nur Umsetzung, Verweise auf neue Pfade und IDs.
5. Vision: Kernsatz aus vorhandenem Text, Abschnitt „Themen“.
6. Profil (Normquellen aus den Requirements), `AGENTS.md`, `CLAUDE.md` mit Verweis.
7. Tests: `@Tag` → `@DisplayName`, parametrisierte Tests mit `{displayName}`.
8. Build: eigenes Gate ersetzen, im Reactor als letztes Modul; CI anpassen.
9. Prüfen ohne Tests, dann der volle Build wie in der CI.

**Zuschnitt der ersten Fassung (2026-10-05).**
- `spine-adopt` zieht nur die Doku um. Tests, Build und CI (Punkte 7 und 8) übernimmt
  `spine-gate`, das dafür ein vorhandenes Traceability-Gate ablösen kann. So gibt es die
  Build-Anbindung nur an einer Stelle (ADR-0010).
- Erst Bestandsaufnahme, dann ein Plan mit einem Ziel je Datei, eine Freigabe. Dateien
  werden in einem eigenen Commit verschoben, bevor sich Inhalt oder Format ändern, damit
  die History bleibt.
- Vorher sauberer Stand: keine offenen Änderungen, keine ungemergten Branches.
- Eigene Skills unter `.claude/skills/` vor der Installation nach `.agents/skills/`
  verschieben, sonst kann die Installation ihren Verweis nicht anlegen.
- Große Diagramme bleiben als Quelle mit SVG unter `docs/diagrams/` (Standard 9), keine
  Pflicht zur Umstellung auf Mermaid.
- Ausgelegt auf Projekte mit strukturierter Spezifikation. Freie Prosa geht nach
  `docs/legacy/`; feinere Regeln erst, wenn ein solcher Fall ansteht (US-0012).

**Stand.** Erster echter Lauf ist die Migration des Ursprungsprojekts (US-0013). Was
dabei fehlt, fließt als allgemeine Regel in den Skill zurück; danach `verified`.

**Stand (2026-10-06).** Drei Läufe: Ursprungsprojekt (US-0013), tarifnova und 3dPacMan
(US-0012). Die Regel für freie Prosa ist mit 3dPacMan präzisiert: Requirements in Prosa
bekommen ein EARS-Statement als Vorschlag, der Text bleibt im Body; nur Doku ohne jede
Struktur geht nach `docs/legacy/`.
